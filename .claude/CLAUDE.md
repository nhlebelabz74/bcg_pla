# Bag tracking POC: project context

## Problem

An NGO grows non-fresh produce (maize and similar dry goods), packs it into bags and trucks the bags to a warehouse. Trucks then carry bags from the warehouse to a shop. Both sites close for half a day each week to count bags by hand, and that manual count is the bottleneck. The shop has its own ERP for check-ins and sales, but it does not record which warehouse a bag came from. The warehouse has no system.

This project builds a proof of concept (POC) of a separate RFID system with two jobs. It records every bag entering and leaving each site, which gives book stock and timing insights. It also supports a walk-in count with a handheld reader, so staff can count any day without closing the site. The two check each other.

The demo uses two RC522 readers: R1 reads bags coming in and R2 reads bags going out. The phone moves both readers between six sites: four warehouses (WH1 to WH4) and two shops (SHOP1, SHOP2). About 230 simulated bags fill the network; four real tags move through it live. Dashboards on the projector show the insights. The demo is for a BCG Platinion hackathon.

The walk-in count reconciles the sources. At the shop it compares the count with the RFID records and a simulated ERP, and says which is right. At the warehouse, which has no ERP, it compares the count with the RFID records. Every outcome is recorded and every disagreement is flagged. The gun count is the source of truth for RFID stock: corrections are added as new events, no event is ever edited or deleted, and the ERP is never written. Every bag missing at a count opens an investigation, which closes when the bag is seen again. Shop staff count at closing every day.

## Fixed decisions

- Keep everything in this local folder. Do not use or push to the team repo until the user says so.
- The tag carries only its unique ID. Site, facility type and direction belong to the reader. Product, size and use number belong to the bag cycle in the database.
- Origin is not tracked. The NGO grows all the produce and supplies the equipment.
- The NGO fits tags at packing, so bags arrive tagged. Shop staff remove tags before sale and the tags are reused. Each fill of a tag is a bag cycle, and every insight works per cycle.
- "Out" at the shop means a sale. Production trip IDs are out of scope.
- Two readers only. No more hardware will be bought for the demo.
- The readers connect in one of two ways: both on one Uno through the breadboard (option A), or one reader per Uno, each wired to D10 (option B). Both Unos run the same sketch; `bridge.py --port <port>:R1 --port <port>:R2` says which Uno is in and which is out. The user has never used a breadboard, so give hole by hole help.
- The reader laptop `tmk74` has one USB port, so it uploads one Uno at a time. Another laptop with more ports can hold both Unos.
- Any laptop downloads the bridge and sketch from `https://bcg-pla.banzilenhlebela.co.za/files/bridge.py` and `/files/maize_tracker.ino`.
- Only the user operates the control page (`/control?key=...`). The phone stores the key so every page on it can make changes. Dashboards are open and read only.
- The latest scan decides where a bag is now. Gaps in its history are logged as anomalies, never hidden.
- There is one simulated ERP per shop. It books each live shop arrival and sale automatically, and phone buttons create ERP-only bookings and skipped bookings. It records quantities only, like a real ERP. It is labelled "Simulated ERP" on screen.
- Mock stock for the six sites lives in `inventory.db`, marked simulated, generated by `mock_data.py` with a fixed seed; Clear demo data restores it. Each simulated bag has a hidden real location, which always matches the records, so every simulated sweep is exact; counts differ only through the real tags. WH3 and SHOP2 hold no stock. Pages that change data have an Unlock box for pasting the control key; tag assignment keeps the key requirement (auto mode refused to remove it on a public site). `synthetic.json` holds only the weekly count trend, labelled "Synthetic data for illustration".
- Each bag cycle has a product (SEED or FERT) and a size (5, 10, 15, 20 kg). The bag ID is `PRODUCT-KG-U<use>-<tag ID>`, such as `SEED-20-U1-93B73B38`; U is the use number, never R (R1 and R2 are readers). A sold tag goes to the tag pool. The six real tags (`93B73B38`, `937C2A38`, `F710AD64`, `97F8A564`, `84704E4D`, `2B49D307`, listed in `mock_data.REAL_TAGS`) start as bags in stock at SHOP1; selling one frees it into the pool. "Assign by need" assigns pool tags to quantity, product and size lines, real tags first. The Tags page only lists unassigned tags with an Assign button per row; the user assigns them live on the presenter's laptop, which gets the key by opening any page with `?key=` (the key is then removed from the address bar). Each tag has a history page, `/tags/<tag ID>`, with every use and its route; every bag ID links to it. A warehouse entry without an assignment is flagged.
- Pages sit behind a floating bottom dock: Overview, Warehouses, Shops, Tags, Control. Bag details use the shadcn hover card. Every table sorts and filters (`components/data-table.tsx`). The tag cost comparison is not on the dashboard. Live bags are overdue after 60 seconds in transit.
- Backend: `tracker.py` uses only the Python standard library, plus `pyserial` for live mode. It serves a JSON API on port 8000.
- Frontend: Next.js with shadcn/ui in the Lyra style (`radix-lyra`) and Bklit UI charts with their animations, in `app/`. Next.js proxies `/api/*` to `tracker.py`. Streamlit was rejected because it cannot render Bklit. The global frontend rules in the user's CLAUDE.md apply in full.
- Colours: the BCG Platinion palette (`#0ECA91`, `#8AD9BC`, `#000000`, `#707070`, `#F7EFF1`). Roles, contrast ratios and light and dark mode rules are in `plan.md` under Frontend, Colour. Dark mode is the demo default. Never use green or mint for text or thin lines on the light background.
- `tracker.py` serves only the JSON API. The Next.js app serves the pages: Overview (`/`), `/warehouses`, `/shops`, `/tags` and `/control`. `/dashboard` redirects to `/`.
- Light mode draws green text and lines in `#055A3F`. The `dataviz` validator rejected `#08875F` because it collides with the ERP grey for colour blind viewers.

## Environment

- The server runs on this Linux machine in Docker (`docker-compose.yml`): the tracker and the app in one container on `172.17.0.1:3010`, the database on the volume `bagdata`, the key in `.env`. The wits-tats Cloudflare tunnel (a remotely managed tunnel in `~/Desktop/projects/wits-tats`) publishes it at `https://bcg-pla.banzilenhlebela.co.za` through `host.docker.internal:3010`. Do not change the wits-tats project.
- Update the server with `docker compose up -d --build`. Read the key with `docker compose logs app | grep -i key`. Fly.io (`fly.toml`) and Tailscale Funnel are retired fallbacks.
- Each Uno plugs into a reader laptop that runs `bridge.py` against the public address. If a bridge shows no `read INFO` line after connecting, press the Uno's reset button. Details are in `plan.md` under Machines. The Windows notes below apply to the laptop `tmk74`.
- After any `npx shadcn add @bklit/...`, remove the broken `var(----...)` and oklch lines the CLI writes into `app/globals.css`, and answer no to overwriting `lib/utils.ts`.
- `review-animations` cannot be started by Claude. Ask the user to type `/review-animations`.
- Bklit `bar.tsx` and `ring.tsx` carry local reduced motion patches. Re-adding those charts with the shadcn CLI overwrites them.
- Windows laptop. The Uno appears as COM7 and uses a genuine Arduino USB chip, so no CH340 driver is needed.
- `arduino-cli` 1.5.1 is at `C:\Program Files\Arduino CLI\arduino-cli.exe`. It may not be on PATH in a running session.
- `pyserial` is installed in the user site-packages. Running Python with `-I` hides it, so do not use `-I` for scripts that need it.
- Only one program can hold an Uno's port. Stop the bridge and any serial monitor before uploading.
- Node 24.20.0 and npm 11.6.1 are installed.
- `tracker.py --port COM7` serves the API on port 8000 when the Uno is on the same machine. `POST /api/scan` simulates a tap, so changes can be tested without hardware. `bridge.py --stdin` tests the network link without the Uno.
- Use a scratch database (`--db` pointing at the scratchpad) and a different `--http` port for tests, so `inventory.db` stays clean for the demo. Point a test copy of the app at it with `TRACKER_URL=http://127.0.0.1:<port> npx next dev -p <other port>`.

## Working with the user

- The user is new to Arduino hardware. Explain physical steps concretely: which pin, which socket, which end of a wire.
- Claude Code cannot touch the hardware. Ask the user to tap tags, check LEDs or move wires, then read the serial output or the tracker log to confirm each step.
- Unplug USB before any wiring change. Never connect the RC522 to 5V.
- The user works in a team. Write documents so a teammate can follow them without this conversation.
